# Design note — the continuous-effect layer system (P4.0)

The reference for the continuous-effect engine built in P4.1, populated with Bogles' static cards
in P4.2, and property-tested in P4.3. Phase 4 is the project's designated risk centre (PLAN.md §7):
this note is reviewed **before** any implementation packet starts. Its job is to fix the decisions,
not to teach CR 613.

Two things anchor the design. Downward, CR 613 — the layer algorithm the engine must obey. Upward,
the seams P3.1 already cut: `effectiveKeywords`, `effectivePower`, `effectiveToughness`
(`EffectiveCharacteristics.kt`) are the *only* characteristic reads combat and the SBAs make, and
their KDoc has promised since P3.1 that Phase 4 rewrites their bodies and nothing else. This note is
mostly about what fills the gap between those two, and — deliberately — how little new state it costs.

## 1. Scope: which layers the pool actually exercises

CR 613 has seven layers; layer 7 splits into 7a–7d (CR 613.3). The pinned pool (docs/decklists.md)
exercises **exactly two**: layer 6 (ability adding) and layer 7c (P/T modifications that don't set).
The precise inventory, every continuous effect in either 75:

| Source (Aura) | Layer 6 grant | Layer 7c P/T | Magnitude | Affects |
|---|---|---|---|---|
| Rancor | trample | +2/+0 | fixed | enchanted creature |
| Armadillo Cloak | trample | +2/+2 | fixed | enchanted creature |
| Cartouche of Solidarity | first strike | +1/+1 | fixed | enchanted creature |
| Sentinel's Eyes | vigilance | +1/+1 | fixed | enchanted creature |
| Ethereal Armor | first strike | +N/+N | **dynamic**: N = enchantments you control | enchanted creature |
| Ancestral Mask | — | +2N/+2N | **dynamic**: N = *other* enchantments on the battlefield | enchanted creature |
| Abundant Growth | `{T}: add one mana of any color` (mana ability) | — | — | enchanted **land** |
| Utopia Sprawl | *triggered* mana ability (**P5**, CR 605.1b) | — | — | enchanted Forest |

Everything else is absent and verified so: no copy (1), control-change (2), text (3), type (4), or
colour (5) effect; no characteristic-defining P/T (7a) — `PrintedPowerToughness` already rejects `*`;
no "becomes a 1/1" set-effect (7b); no P/T **switching** (7d). The GameObject KDoc's
"control-changing effects arrive in Phase 4" is aspirational: layer 2 gets a *slot*, never an effect.

> **Superseded by `FW-COUNTERS`.** This paragraph originally read "**no +1/+1 counters anywhere**
> (7d)". Counters (CR 122) now exist, and they were never a 7d concern: **CR 613.4c** puts "effects
> **and counters** that modify power and/or toughness" in sublayer **7c**, alongside the Aura
> modifiers this design already covered, and **CR 613.4d** is P/T *switching*. **There is no rule
> 613.4e** — the citation `Layers.kt` carried was invented, and it had shifted every 7a–7d citation
> in that enum one letter to make room. Checked against the Comprehensive Rules of 2026-08-19 and
> corrected; the enum member is now `PT_SWITCHING`, and 7d remains an unpopulated loud gate because
> no gauntlet card switches power and toughness. A keyword counter (CR 122.1b) lands in layer 6 by
> the same reading of CR 613.1f that granted keywords already used.

**Decision — full skeleton, sparse population.** The apply loop implements the entire ordered spine,
layers 1→7 and sublayers 7a→7d, as real ordered stages (PLAN.md §6 P4.0: "implement the full
algorithm"). Only the layer-6 and layer-7c stages carry effect kinds. A continuous effect that
classifies into any other layer, or an effect kind not on the closed list above, hits the loud
`error(...)` gate (CONVENTIONS.md loud-failure rule) — never a silent drop.

## 2. What a continuous effect is (representation)

Every MVP continuous effect is generated by a **static ability of a permanent** (CR 604.3, 611.2) —
concretely, an Aura's "enchanted X gets/has …". It is active exactly while the Aura is on the
battlefield attached to a legal object; there is no resolution-generated or floating effect in the
pool. That collapses the representation enormously.

**Core/rules split (ADR-009: "no game-rule decisions in core").** The *declaration* is card-definition
data and rides in `GameState` with the rest of the definition, so it lives in `mtg-core`; the
*classification into layers* and the *application* are CR 613 rules logic and live in `mtg-rules`.
Core says what an ability does; rules decides which layer that lands in. So `mtg-core` gains a noun
on `CardDefinition` roughly:

```kotlin
// mtg-core — a static ability's continuous effect, as data. No layer, no CR 613 here.
data class StaticContinuousEffect(
    val affects: AffectedSet,             // MVP: only AffectedSet.Enchanted
    val grantedKeywords: PersistentSet<Keyword> = persistentSetOf(),
    val grantedManaAbilities: PersistentList<ManaAbility> = persistentListOf(),
    val powerMod: Magnitude = Magnitude.Zero,
    val toughnessMod: Magnitude = Magnitude.Zero,
)
sealed interface Magnitude {                // fixed vs dynamic
    data class Fixed(val amount: Int) : Magnitude
    fun interface Dynamic : Magnitude {     // pure fn of state, ADR-009 pattern (cf. ResolutionEffect)
        fun evaluate(state: GameState, source: ObjectId): Int
    }
}
```

- **Applicability** is `AffectedSet.Enchanted` for every MVP effect — the one object the Aura is
  attached to. `Self` and computed-set selectors (e.g. "other creatures you control") are not needed
  and are not built; the sealed `AffectedSet` is the extension point.
- **Fixed vs dynamic magnitude.** Ethereal Armor and Ancestral Mask are the only dynamic ones. Their
  count is a `Magnitude.Dynamic` — a pure function of the current `GameState`. **It is not a snapshot:**
  a 7c modifier's value is read from the live state every time characteristics are computed
  (CR 613.3c — 7c effects apply continuously). Ethereal Armor's bonus therefore tracks the current
  enchantment count with no explicit recompute. This semantics falls out for free from §5's
  compute-on-read strategy; it is the reason the two are linked decisions.
- **Duration** is uniformly "while the generating static ability is active" — i.e. while the Aura is
  attached. No effect has an until-end-of-turn or fixed-duration shape. **Decision: build no duration
  machinery.** Until-EOT arrives later with Tamiyo's Safekeeping (sideboard, Phase 5+); the hook is
  the effect-*collection* step (§3), which today reads only battlefield statics and later concatenates
  a second, timestamped, expiring source without reshaping anything downstream.

## 3. The algorithm

To compute an object's characteristics: take its printed values as the base (CR 613.2 — no copy
effects, so the copiable values *are* the printed ones), then apply active continuous effects layer
by layer, 1→7, and within layer 7, 7a→7d (CR 613.1, 613.3). Within one layer, order by timestamp
(CR 613.7), then resolve dependencies (CR 613.8). For the MVP only the layer-6 and 7c stages act:
layer 6 unions granted keywords/abilities onto the object; 7c adds the (possibly dynamic) power/
toughness modifiers.

**Timestamps — decision: source them from battlefield-entry order (the fresh `ObjectId` minted on
entry), add no new state field.** CR 613.7c makes an Aura's timestamp the moment it became attached.
In the MVP an Aura *enters the battlefield already attached* (CR 303.4f) and nothing ever re-attaches
it, so "attached" and "entered" coincide exactly, and entry order is `ObjectId` order — monotonic,
deterministic, replay-safe (ADR-006) by construction. Two reasons this is not just expedient but
*correct*: (a) attachment == entry for every MVP Aura; (b) **every within-layer MVP interaction
commutes** — 7c modifiers are integer additions, layer-6 grants are set unions — so timestamp order
is not even observable yet. The apply loop still sorts by this timestamp (the 613.7 spine is real, so
P4.3 can assert it), it simply needs no dedicated counter to feed it. An explicit timestamp field is
deferred to the first re-timestamping effect (Aura re-attachment; copy, CR 613.7f); the single
timestamp accessor is where it slots in.

**Dependency (CR 613.8) — verdict: defer, and it is correct-by-construction, not a guess.** No
interaction in either 75 creates a dependency. A 613.8 dependency needs two effects in the same layer
where applying one would change *whether the other exists, what it applies to, or what it does* — the
textbook case is a layer-6 "loses all abilities" against a layer-6 "has flying". The pool has only
*additive* layer-6 grants and *additive* 7c modifiers. Crucially, the two dynamic auras are **not**
a dependency: Ethereal Armor counts enchantment *permanents* you control and Ancestral Mask counts
*other* enchantment permanents — each reads the set of enchantments that simply *exist* on the
battlefield, which no effect's *application* changes. Adding a second aura raises both counts because
another permanent is present, not because one effect was applied before the other; and since 7c is
additive the two commute regardless. So among the closed set of implemented effect kinds a dependency
is structurally impossible. **The loud gate is therefore the same gate as everywhere else:** any
effect kind that *could* induce a dependency (ability removal, set-P/T, type-change) is off the
implemented list and hits the existing `error("CR 613.8 dependency ordering not yet supported: …")`.
Full dependency ordering is real work, untestable against this pool, and speculative; it lands with
the first card that needs it.

## 4. Aura attachment substrate

Auras are new state: today only lands reach the battlefield, and `GameObject` carries no attachment.
An Aura is an enchantment (a permanent, non-instant/sorcery) so it already flows through the existing
permanent-spell resolution path (`putResolvedSpellOntoBattlefield`); what is new is that it targets
the object it will enchant while on the stack (CR 601.2c) and **enters attached** to it (CR 303.4f).

- **The relation — decision: `attachedTo: ObjectId?` on `GameObject`.** It is the Aura's own status,
  battlefield-scoped, and — exactly like `tapped`/`damageMarked`/`summoningSick` — it is dropped when
  the object is reborn on any zone move (CR 400.7). The inverse ("what is on this creature") is a
  battlefield scan, matching the existing "battlefield has no rules-relevant order, scan it" pattern.
  A separate attachment map in `GameState` was rejected: it would duplicate the object's lifecycle and
  need its own zone-move cleanup.
- **Enchant restrictions — decision: a new `TargetSpec` member** (`Enchantable(restriction)`) reusing
  the existing target enumeration + CR 608.2b re-check (ADR-005). The MVP restrictions — creature,
  land, Forest (subtype), creature-you-control — are noun-level predicates over printed characteristics
  plus control. **Control == ownership** for now: no control-changing effect exists (§1), so
  "creature you control" is `owner == caster`; the seam is noted for when layer 2 gains an effect.
- **Falling off — CR 704.5m, in P4.1 scope (not P5).** An Aura attached to an illegal object or to
  nothing goes to its owner's graveyard as a state-based action. This is unavoidable the moment auras
  exist: P3.2 combat already kills creatures, and an Aura on a dead creature must leave immediately.
  It is a new `StateBasedAction` member checked beside the creature-death checks. It composes with the
  fresh-id rule automatically: when the enchanted creature dies it is reborn in the graveyard with a
  new id, the Aura's `attachedTo` now names no battlefield object, and 704.5m fires on the next check.
  (CR 704.5n, the Equipment analogue that merely unattaches, has no member in the pool.)

## 5. Computation strategy under immutability

**Decision: compute-on-read.** The `effective*` accessors walk active effects on each call; no
computed characteristic is ever stored in `GameState`. Rationale:

- **Correctness / no stale reads.** Dynamic magnitudes depend on the whole battlefield; a materialised
  cache would need invalidation on every aura/creature enter-or-leave. Under structural-sharing
  immutability there is no mutation hook to invalidate on — you would recompute-and-store every
  transition anyway (strictly more work) while adding the one failure mode PLAN.md §7 calls the worst:
  a forgotten recompute is silently-wrong-but-plausible state. Compute-on-read makes a stale read
  impossible: every read reflects current state by construction, which is also exactly the CR 613.3c
  continuous-reevaluation semantics §2 needs.
- **Fingerprint / replay (resolves the P3.3 flag).** The flag asked that states differing in
  continuous effects not hash alike. **Decision: digest the *cause*, not the *effect*** — add each
  battlefield object's `attachedTo` to the fingerprint's per-object line; do **not** digest computed
  P/T or keywords. The argument: computed characteristics are a pure function of state the digest
  already covers (printed cards of every battlefield object, plus attachment). Two states with
  different continuous effects necessarily differ in which auras are present or what they are attached
  to — already in the digest — so they already hash apart, and digesting computed P/T would be
  redundant *and* would re-implement layer logic inside `mtg-acceptance`. Minimal change: one new
  token, `attachedTo`, on the residence line beside `:tapped`/`:dmg`.
- **Performance under fuzz.** Compute-on-read means the enumeration probe re-measures characteristics
  at its stride. The battlefield is tiny (a Bogles board is a handful of permanents), so each read is
  O(board). Acceptable now; if profiling flags it, the fix is a *transient* per-pass memo (compute all
  objects' layered characteristics once at the top of an enumeration pass, thread it as a local),
  never a stored cache — state stays pure and the fingerprint stays minimal.
- **Simplicity.** One function, `layeredCharacteristics(state, id)`, that the three accessors delegate
  to. No invalidation, no coherence, no stored field beyond `attachedTo`.

**Invariant / fuzz routing.** `CREATURE_LETHALITY_RESOLVED` and the fuzz lethality classification
today read *printed* toughness; P4.1 reroutes both to layered toughness (the P3.3 flag; the invariant
KDoc already anticipates this). Because those live in `mtg-acceptance`, P4.1 exposes a **public**
`layeredCharacteristics`/`layeredToughness` in `mtg-rules` that both the internal combat accessors and
acceptance consume — one source of truth, no duplicated layer logic. (New public rules surface;
flag in the packet report. `mtg-acceptance` already depends on everything.)

## 6. Seam replacement plan

- `effectiveKeywords(state,id)` → printed keywords ∪ layer-6 grants active on `id`.
- `effectivePower` / `effectiveToughness` → printed base with layer-7c modifiers summed (dynamic
  magnitudes evaluated against current state). The non-creature loud-fail contract is unchanged.
- **New seam: `productionProfile`** (payment enumeration) must include layer-6 *granted* mana
  abilities, not only `definition.manaAbilities` — this is how an Abundant-Growth-enchanted land gains
  `{T}: add one mana of any color`. Its KDoc currently says "Phase 5"; that refers to Utopia Sprawl's
  *triggered* mana ability. The plain (non-triggered) grant is layer 6 and is a genuine P4 caller —
  noted so the seam's own doc is corrected in P4.
- **No new layered caller for targeting in P4.** Enchant-restriction legality read *printed* types/
  subtypes, because no type-changing effect existed. Keyword-driven targeting (hexproof) is P5.2.

  **Superseded by `FW-TYPECHANGE`.** Layer 4 is populated and enchant-restriction legality now reads the
  layered type line. It is the sharpest of the rerouted reads rather than the mildest: the same predicate
  is both cast-time target legality (CR 601.2c) and the CR 704.5m fall-off state-based action, so a
  printed read would let an Aura legally enchant a permanent a type-changing effect had made a creature
  and then have the SBA bin the Aura for enchanting something illegal.
- **Unchanged: every combat/SBA call site** in `CombatDamage.kt` and `StateBasedActions.kt`. They keep
  calling the same three accessors; only the bodies change. That is the P3.1 contract, kept.

## 7. Packet boundaries

- **P4.1 — framework** (`mtg-rules` + `mtg-core` state + `mtg-acceptance` rerouting). Continuous-effect
  engine and aura substrate, exercised by rules-module fixture auras (no card names — the
  `mtg-rules`-names-no-card rule holds). *Accept:* fixture "+X/+Y & grant keyword" aura computes correct
  layered P/T and keywords; a fixture mana-ability-granting aura makes an enchanted land tap for the
  granted mana (the layer-6-on-non-creature capability the decklists tag to Abundant Growth); an aura
  on a creature that dies is put to graveyard by 704.5m at the next SBA check; the three `effective*`
  seams and `productionProfile` route through the layer engine; an effect in an unpopulated layer
  throws; the lethality invariant and fingerprint route through layered/attachment state.
- **P4.2 — Bogles statics** (`mtg-cards`). The real auras as DSL definitions: Rancor's static half,
  Armadillo Cloak, Cartouche, Sentinel's Eyes, Ethereal Armor, Ancestral Mask, Abundant Growth (each
  a `StaticContinuousEffect`; dynamic magnitudes as pure count functions). *Accept:* each card's
  P/T + keyword/ability grant is correct; the multi-aura timestamp scenarios (§8) pass.
- **P4.3 — layer property tests** (`mtg-acceptance`). Random effect sets → CR 613 ordering properties
  (§8), plus a brute-force oracle. *Accept:* oracle set-equals the engine over random boards; the
  named scenarios pass; fuzz corpus with auras is clean.

## 8. Test strategy

**Property tests (P4.3), in the mana-payment.md oracle style.** A naïve oracle — printed base + sum of
every attached additive modifier, union of every grant — set-compared to the layer engine over random
fixture boards, proving both directions. On top: **order-independence** (any timestamp permutation of a
board yields identical characteristics — the property that *justifies* the deferred-timestamp decision;
its failure means a non-commuting kind slipped in), **layer isolation** (grants never move P/T, mods
never touch keywords), **additivity** (power = printed + Σ mods), **purity** (recomputing on the same
state is identical), and the **loud gate** (an effect in an unpopulated layer throws, never drops).

**Named multi-aura scenarios (from the decklists).**
- *Two Ethereal Armors on one creature:* each counts both auras as enchantments you control → +2/+2
  each → +4/+4 total, first strike once; assert attach order is irrelevant.
- *Ethereal Armor + Ancestral Mask on one creature:* Ethereal Armor sees two enchantments you control
  (+2/+2); Ancestral Mask sees one *other* enchantment (+2/+2); assert the concrete total and that it
  is attach-order-independent.
- *Aura leaves mid-combat → lethality recomputes:* a creature kept alive by a toughness aura; the aura
  is destroyed after damage is marked; `effectiveToughness` drops and the CR 704.5g death SBA now
  fires on the same check — the headline no-stale-read case, tying §5 to combat.
- *Dynamic recount on a new aura:* a second enchantment enters and Ethereal Armor's bonus jumps with
  no explicit recompute call (CR 613.3c continuous reevaluation).

**Fuzz corpora.** Once P4.2 lands, the mixed-matchup corpus gains the Bogles auras; random legal
playouts will enchant creatures, and the attachment-integrity invariant + layered-toughness lethality
+ `attachedTo` in the fingerprint guard the churn (creatures dying with auras → 704.5m). P4.1 fuzzes
fixture auras; the dynamic-count interactions become meaningful only with the P4.2 cards.

## Non-goals (explicit)

Out of design scope, with where each would slot: **copy** (layer 1), **control-change** (layer 2 —
note the GameObject KDoc), **text-change** (3), **type-change** (4), **colour-change** (5),
**characteristic-defining P/T** (7a), **set-P/T "becomes a 1/1"** (7b), **P/T switching** (7d) — no
gauntlet card switches power and toughness (**counters** were listed here as 7d and are neither out of
scope nor 7d any longer: `FW-COUNTERS` implemented them at 7c per CR 613.4c and at layer 6 per
CR 122.1b); **totem armor** — not in the final decklists; **until-EOT / fixed
durations** — deferred with Tamiyo's Safekeeping, hooked at the effect-collection step (§2); **Utopia
Sprawl's triggered mana ability and its "choose a colour" linked info** — P5 (its static "enchant
Forest" attachment *is* P4.1 substrate; only the grant is deferred). Each is a layer *slot* the
skeleton reserves and a loud gate refuses to fake.

## Open questions for the architect

1. **Timestamp sourcing** (§3): reuse `ObjectId`-entry order and add no field (recommended;
   correct for the whole MVP), versus an explicit timestamp counter now for future-proofing. Main call.
2. **Attachment shape** (§4): `attachedTo: ObjectId?` on `GameObject` vs. a separate attachment map.
3. **Public layered accessor** (§5): confirm a new public `layeredCharacteristics` in `mtg-rules`
   consumed by `mtg-acceptance`, with the internal combat accessors delegating to it.
4. **Enchant restriction** (§4): a new `TargetSpec.Enchantable` member vs. a separate `EnchantSpec`
   on the aura definition.
5. **Fingerprint reinterpretation** (§5): digest the `attachedTo` *cause*, not computed P/T — confirm
   this satisfies the P3.3 flag.
6. **Abundant Growth placement**: the decklists tag it P4.1; the `mtg-rules`-names-no-card rule puts
   the *capability* in P4.1 (fixture) and the *card* in P4.2 (`mtg-cards`). Confirm that reading.
