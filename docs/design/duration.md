# Design note — until-end-of-turn continuous effects (`FW-DURATION`)

The design note for the duration framework, written before its implementation packet (PLAN.md §5).
It extends [`layer-system.md`](layer-system.md) — and **reverses one of its decisions** — so that
note and this one must be read together: everything about CR 613 layer classification, timestamps
within a layer, dependency deferral, and compute-on-read stands unchanged. What changes is where the
*set of active continuous effects* comes from.

Its three anchors. Downward, **CR 611.2** — continuous effects generated by the resolution of a spell
or ability — and **CR 514.2**, the cleanup turn-based action that ends them. Upward, the one seam
`layer-system.md` §2 promised for exactly this moment:

> **Decision: build no duration machinery.** Until-EOT arrives later with Tamiyo's Safekeeping
> (sideboard, Phase 5+); the hook is the effect-*collection* step (§3), which today reads only
> battlefield statics and later concatenates a second, timestamped, expiring source without
> reshaping anything downstream.

Sideways, [`protection.md`](protection.md) §3 Part C, which costed a near-identical store a year of
packets ago and is a genuine head start (§2.3).

---

## 0. Oracle text first, and where the triage is wrong

Every card in this packet was re-fetched from `POST https://api.scryfall.com/cards/collection`
(descriptive `User-Agent`, 7/7 found, `not_found` empty) before any code was written. Oracle text
beats both `docs/gauntlet-card-triage.md` and the packet brief. Four disagreements, none fatal but
two load-bearing:

| Card | What the triage/brief says | What the oracle says |
|---|---|---|
| Basilisk Gate | "a resolution-generated until-EOT pump with a **snapshotted** magnitude, plus sorcery timing and a target on an activated ability" | Confirmed, and **it is a land with its own mana ability** — `{T}: Add {C}` *and* `{2}, {T}: Target creature gets +X/+X…`. That second fact is trap **T17**, not a duration problem (§9.1). |
| Timberwatch Elf | "The Basilisk Gate shape on a creature" | Confirmed, and **strictly cheaper**: `{T}` alone, no mana component, no timing restriction. It is Basilisk Gate minus both of Basilisk Gate's non-duration blockers, which makes it — not the Gate — this framework's demonstration card. |
| Brinebarrow Intruder | "Targeted ETB granting an until-EOT `-2/-0`" | Confirmed, but the target is "target creature **an opponent controls**" — a *decider-relative* permanent restriction that does not exist (§9.2). The triage row omits it. |
| Goblin Bushwhacker | "Kicker with linked information, an until-EOT team pump, and an `AffectedSet` wider than `Enchanted`; also haste" | Confirmed in full. Four frameworks, none of them this one. Dropped (§9.4). |
| Toxin Analysis | "Until-EOT deathtouch + lifelink grant on a target, plus a Clue token" | Confirmed. `Keyword.LIFELINK` exists; **`Keyword.DEATHTOUCH` does not**, and deathtouch is a CR 702.2b change to combat-damage lethality, not a keyword flag (§9.3). |
| Tamiyo's Safekeeping | "the forcing function for until-EOT durations; also needs indestructible and a target spec" | Confirmed, and `Keyword.INDESTRUCTIBLE` and `Keyword.HEXPROOF` both now exist — so the *grant* half is buildable. The blocker is the target spec: "target permanent **you control**" (§9.2). |
| Rally at the Hornburg | "the tokens are Tier-0; 'Humans you control gain haste until end of turn' is an until-EOT effect over a computed set, plus haste" | Confirmed (§9.5). |

The pattern is the one prior packets found: the triage is right about *which* framework a card sits
in and unreliable about *how many other* frameworks it also needs. Six of these seven need at least
one framework this packet does not own.

## 1. The gap, precisely

`layer-system.md` §2 fixed a representation in which **duration is not expressible**:

- A continuous effect is a `StaticContinuousEffect` hanging off a `CardDefinition`. It carries no
  timestamp and no duration, because it needs neither: it is active exactly while its source
  permanent is on the battlefield with a non-empty affected set.
- `activeEffectsOn(state, id)` derives the whole active set by scanning the battlefield for Auras
  whose `attachedTo` names `id`. There is nowhere for an effect with no permanent to live.
- Timestamps are the *source permanent's* `ObjectId` — battlefield-entry order. A
  resolution-generated effect has no source permanent whose entry could serve.
- `TurnBasedActions.cleanupRemoveDamageAndEndEffects` clears marked damage and its KDoc says
  `"Until end of turn" / "this turn" effects arrive in Phase 4 and end here too` — an empty half of a
  function named for two jobs.

So today the engine can express "this creature is +2/+2 while an Aura is attached" and cannot express
"this creature is +2/+2 until end of turn". The gap is one type, one state field, one collection
branch, and one cleanup line — but it is also the first time the engine holds a rules-relevant fact
that is not attached to an object, which is why it needs an invariant and a fingerprint token of its
own.

### 1.1 Scope

**In:** resolution-generated (CR 611.2) continuous effects with the single duration
`until end of turn` (CR 514.2), classifying into the two layers `layer-system.md` §1 already
populates — layer 6 keyword grants and sublayer 7c P/T modifiers — with **snapshotted** magnitudes
(CR 611.2d, CR 608.2h). Explicit timestamps in one total order with the existing Aura timestamps
(CR 613.7d). The CR 514.2 wear-off, and its simultaneity with damage removal.

**Out, and loud-gated rather than faked:** every other duration (§12); `AffectedSet` selectors wider
than one named object; CR 615 prevention shields (§2.3); delayed triggered abilities (CR 603.7);
"until your next turn" / "until end of your next turn" (Reckless Impulse, Clockwork Percussionist);
CR 613.8 dependency ordering, which stays deferred on exactly `layer-system.md` §3's argument.

## 2. Reversing "build no duration machinery"

### 2.1 Why the original decision was right, and why it has expired

`layer-system.md` §2 made the call against a pinned two-deck pool in which **every** continuous
effect was an Aura's static ability. In that pool duration machinery would have been state with no
producer: a `GameState` field always empty, an invariant that could never fire, a fingerprint token
that never varied, and a cleanup branch no test could reach. Refusing to build it was not laziness;
it was the same discipline that left layers 1–5 as empty ordered stages.

The premise expired the moment the gauntlet arrived. `docs/gauntlet-card-triage.md` §5 counts
**thirteen** Tier-2 cards naming `FW-DURATION`, across **seven** mainboards, and the note's own
nominated forcing function (Tamiyo's Safekeeping) is no longer alone — `cost-modification.md` §7 found
a second in a *maindeck*:

> **Duration.** "Decision: build no duration machinery" (§2), hooked at the effect-collection step,
> with Tamiyo's Safekeeping named as the forcing function. Basilisk Gate is a second one, in a
> maindeck.

So the reversal is not a re-litigation of the original reasoning. It is the trigger the original
reasoning named, firing.

### 2.2 What the reversal costs, and what it does *not* cost

The reversal is deliberately narrow, and the measure of a good hook is how little of §§3–6 of
`layer-system.md` it disturbs. Concretely, **nothing downstream of effect collection changes**:

| `layer-system.md` decision | Status after this packet |
|---|---|
| §3 full layer skeleton, sparse population, loud gate | **Unchanged.** A timed effect classifies into layer 6 or 7c through the same `layersOf`, and hits the same `error(...)` if it would not. |
| §3 within-layer timestamp sort | **Unchanged in shape, extended in source.** §4 below. |
| §3 CR 613.8 dependency deferral | **Unchanged**, and still correct-by-construction: a timed grant is additive and a timed modifier is additive, so the closed set of effect kinds still contains no dependency. |
| §5 compute-on-read, nothing cached | **Unchanged**, and now load-bearing twice over (§6). |
| §5 fingerprint digests the *cause*, not the effect | **Unchanged in principle**, and it is precisely this principle that forces a new token (§7): a timed effect *is* a cause, and it is the first cause that is not an object. |
| §6 the three `effective*` seams | **Unchanged.** They keep calling `layeredCharacteristics`; only the set of effects it collects grows. |
| §4 Aura substrate, CR 704.5m fall-off | **Untouched.** |

The one genuine reversal is §2's sentence, and the one genuine *addition* is state that does not hang
off an object.

### 2.3 The head start from `protection.md` §3, and one thing it does not transfer

`protection.md` §3 Part C already costed this store, for a different consumer:

> **Part C — the prevention *effect store*, needed by Prismatic Strands and nothing else in F2.** A
> resolution-generated, turn-duration, non-characteristic continuous effect (CR 615.3 …). This is new
> state on `GameState`, cleared in the cleanup step (CR 514.2), plus a new invariant (DoD item 4) and
> a new fingerprint token, plus the `layer-system.md` §2 decision "**build no duration machinery**"
> being consciously reopened. Size: **medium** …

Every structural claim there holds here, and this note adopts them: `GameState` field, CR 514.2
clear, new invariant, new fingerprint token, medium. Two of its findings transfer verbatim and are
worth restating because they save real work:

- **No CR 616.1 ordering choice.** With only additive grants and additive modifiers, every ordering
  of the applicable effects produces the identical characteristics, so order is unobservable. This is
  the same commutativity argument `layer-system.md` §3 makes for Aura timestamps, and it is
  correct-by-construction over a closed list, not a guess. A non-commuting effect kind (ability
  *removal*, set-P/T) is off the list and meets the existing loud gate.
- **No numeric shields.** CR 615.7 "prevent the next N damage" needs a which-shield-absorbed-it
  choice. Nothing here has one.

**What does not transfer, and matters:** a CR 615 prevention shield is **not a CR 613 continuous
effect at all.** CR 613.1 lists the characteristics layers apply to — copiable values, control,
text, types, colour, abilities, P/T — and "damage is prevented" is none of them. A prevention effect
is consulted at the damage event (`protection.md` §3 Part B's application point), never in the layer
walk. So when `FW-PREVENT` lands it may share this note's **duration and cleanup machinery** —
the store, the timestamp, the CR 514.2 wear-off, the invariant, the fingerprint token — and must
**not** share `activeEffectsOn`. This note therefore keeps the two apart by construction: the store
holds *characteristic-modifying* effects and the `EffectKind` that would carry a shield does not
exist. `FW-PREVENT` adds one, and the layer collector's exhaustive `when` refuses it until the damage
application point reads it. Naming that now is the cheap half of not building it.

## 3. Snapshotted vs dynamic — the ruling that makes Basilisk Gate right

This is the section the framework turns on. `docs/gauntlet-card-triage.md` T16 states the failure
mode, and `cost-modification.md` §6 states the cause:

> reusing the existing `Magnitude.Dynamic` for Basilisk Gate — the obvious move, since it is the one
> dynamic-count type the engine has — gives the +X/+X a value that **tracks the Gate count for the
> rest of the turn**. Play a fourth Gate and the pump grows; lose one and it shrinks. The game state
> stays internally consistent, no invariant fires, no test that is not looking for it fails.

### 3.1 The rules distinction

Two CR paragraphs, and they point in opposite directions.

- **CR 613.3c / CR 613.5** — a continuous effect generated by a *static ability* is re-evaluated
  continuously. Ethereal Armor's "+1/+1 for each enchantment you control" reads the live board every
  time characteristics are computed. That is `Magnitude.Dynamic`, and it is correct.
- **CR 608.2h + CR 611.2d** — a spell or ability that sets a value using a variable **calculates it
  once, on resolution**, and the continuous effect it creates uses that calculated value for its
  whole duration. Basilisk Gate's X and Timberwatch Elf's X are fixed the instant the ability
  resolves; the board may change afterwards and the pump does not.

Both cards *look* like Ethereal Armor — a count of permanents feeding a P/T modifier — and the
difference is invisible on a board where the count never changes, which is most boards. That is the
"wrong result that looks right" PLAN.md §7 names as the worst outcome.

### 3.2 The decision: a snapshot is not a kind of magnitude — it is the *absence* of one

The tempting design is `Magnitude.Snapshot(...)`, a third member beside `Fixed` and `Dynamic`. It is
wrong, and the reason is timing rather than taste: a snapshot is taken **at effect creation**, which
happens strictly *before* the layer engine ever sees the effect. By the time `applyContinuousEffects`
runs, there is nothing left to evaluate. A `Magnitude.Snapshot` member would therefore be a value
whose "evaluate" is the identity function — a `Fixed` with extra ceremony, and one more branch that a
future author could route a live read through.

**Decision: a timed continuous effect stores `powerMod: Int` and `toughnessMod: Int` as plain
integers, and the count is performed by the *resolution effect* that creates it.** `Magnitude` is not
mentioned in the new type at all. The consequences are exactly the ones wanted:

- The snapshot is **unrepresentable-otherwise**: there is no way to put a state-reading function into
  a timed effect, so `Magnitude.Dynamic` cannot be reused by accident. T16's failure mode is a type
  error rather than a review catch.
- The read point is where CR 608.2h puts it: inside `ResolutionEffect.resolve`, which already has the
  state and the `ResolutionContext`, and which already performs exactly this kind of read for Skred's
  snow count and Galvanic Blast's metalcraft threshold.
- The layer engine needs **no** new evaluation path. When the collector lifts a timed effect into an
  `ActiveEffect` it presents the integers as `Magnitude.Fixed`, which is not a conversion so much as
  an admission of what they already are.

This is `cost-modification.md` §6's verdict applied at the type level: *one counting noun, four
consumers, each naming its own read point in its own type.* The counting noun is the
`PermanentFilter`/count pair that already exists for mana production (§5.3); the read point is stated
by which type the count lands in — `Magnitude.Dynamic` for a live static, a bare `Int` for a
snapshot.

### 3.3 The property that pins it

The distinction is only real if a test can see it, so the test is named before the code:

> **CR 611.2d: an until-end-of-turn pump does not track the board after it resolves** — Timberwatch
> Elf taps for +2/+2 with two Elves out; a third Elf then enters; the pumped creature is still +2/+2,
> not +3/+3.

Its mirror, proving the *other* semantics is not broken by this packet:

> **CR 613.3c: an Aura's dynamic magnitude still tracks the board** — the existing Ethereal Armor
> recount case, re-asserted on a board that also carries a timed effect.

Running both on the same board is what makes the two semantics visibly different rather than merely
documented as different.

## 4. Timestamps — one sequence, and why a second counter would be a bug

`layer-system.md` §3 decided that a timestamp is the source permanent's battlefield-entry order, i.e.
its `ObjectId` value, and added no field. Its own open question 1 asked whether that would survive.
`cost-modification.md` §7 answered:

> **Explicit timestamps.** layer-system.md §3's decision — reuse battlefield-entry `ObjectId` order,
> add no field — is justified by every MVP effect having a permanent whose entry *is* its timestamp.
> A resolution-generated effect has no such permanent. This retires that decision and answers
> layer-system.md's own open question 1.

CR 613.7d gives the rule: a continuous effect generated by the resolution of a spell or ability
receives a timestamp *at the time it is created*.

**The decision: mint a timed effect's timestamp from the existing `GameState.nextObjectId`
allocation counter, via `allocateObjectId()`.** No new counter, no new field on `GameState` beyond
the store itself.

The reason is not economy — it is correctness. CR 613.7 requires a **single total order** over every
effect in a layer, and an Aura's timestamp is already an `ObjectId` value. A separate
`nextTimestamp` counter would produce two independent sequences whose values are not comparable:
"Aura 7 vs timed effect 3" would have no meaning, and the sort would silently order by an
accident of which counter each came from. Drawing both from one strictly-monotonic sequence makes
"the Aura entered before the ability resolved" and "the ability resolved before the Aura entered"
different, correct answers. Two further properties fall out: the counter is already replay-safe and
already digested by the fingerprint (`|nextObjectId=`), so timestamp allocation needs no new
determinism argument (ADR-006).

The cost is that the id space advances for something that is not an object. `ObjectId` is a `Long`
and CR 400.7 forbids *reuse*, not gaps, so the only real objection is naming — and the counter is
better understood as the engine's monotonic creation sequence, of which object birth is one client
and effect creation is now a second. The `GameState` construction invariant ("every id in the state
is strictly below the counter") is unaffected: a timestamp is not an id in any zone.

**Observability today: none, and that is stated rather than assumed.** Every implemented effect kind
is additive — a set union in layer 6, an integer addition in 7c — so all within-layer orders agree.
The sort is performed anyway because the CR 613.7 spine is real, and the order-independence property
test (§10) is what would catch a non-commuting kind slipping in. This is the same argument
`layer-system.md` §3 made, with a strictly larger effect set, and it is still
correct-by-construction over the closed list.

## 5. The model

### 5.1 The new state, in core

Two new `mtg-core` nouns, in `core/state/` rather than `core/definition/` because — unlike
`StaticContinuousEffect` — this is not something a card *declares*, it is something the game
*contains* at a moment in time.

```kotlin
// mtg-core/state/EffectDuration.kt
sealed interface EffectDuration {
    data object UntilEndOfTurn : EffectDuration   // CR 514.2
}

// mtg-core/state/ContinuousModification.kt — *what* the effect does
data class ContinuousModification(
    val grantedKeywords: PersistentSet<Keyword> = persistentSetOf(),  // layer 6 (CR 613.1f)
    val powerMod: Int = 0,                        // sublayer 7c, ALREADY SNAPSHOTTED (CR 611.2d)
    val toughnessMod: Int = 0,
)

// mtg-core/state/TimedContinuousEffect.kt — *what*, *to what*, and *until when*
data class TimedContinuousEffect(
    val affected: ObjectId,                       // CR 611.2c: locked at creation
    val modification: ContinuousModification,
    val duration: EffectDuration,
    val timestamp: Long,                          // CR 613.7d
    val createdOnTurn: Int,                       // what the invariant checks
    val source: ObjectId?,                        // narration + fingerprint; CR 113.7c LKI
    val sourceCard: CardRef,
)
```

The payload is split out as [`ContinuousModification`] rather than inlined for two reasons: it is
the counterpart of `StaticContinuousEffect`'s grant/modifier fields and reads as one, and it is the
natural home for the "an effect must do *something*" gate — the loud gate of
`layer-system.md` §1, enforced at construction so an empty effect is unrepresentable rather than
merely refused later.

and one new field:

```kotlin
val timedEffects: PersistentList<TimedContinuousEffect> = persistentListOf()
```

Four shape decisions worth their lines.

- **`affected` is one `ObjectId`, not an `AffectedSet`.** CR 611.2c fixes the affected set when the
  effect begins; for every card this framework carries that set is the single target the CR 608.2b
  re-check has just confirmed. A computed set ("creatures you control") is `FW-CONDSTATIC`, needs a
  wider `AffectedSet`, and is deliberately not built (§12) — so the narrow type is what stops it
  being half-built.
- **No `AffectedSet.Enchanted` lie.** An earlier draft reused `StaticContinuousEffect` as the payload
  and stored `affects = Enchanted` in it because the field has that default. That value would be
  false, and would be read by anything that later walked the store generically. The store carries the
  affected object directly.
- **`grantedManaAbilities` is absent.** No card in the gauntlet grants a mana ability for a turn.
  Adding an always-empty field would be an untested branch of the layer-6 union; the field arrives
  with the card that prints it.
- **`createdOnTurn` exists solely for the invariant** (§8). It is derivable from nothing else once
  the turn advances, which is exactly why the check needs it: without it, "this effect should have
  worn off" is not a checkable statement.

### 5.2 Collection — the hook `layer-system.md` promised, taken

`activeEffectsOn(state, affectedId)` gains a second source, concatenated after the battlefield
statics. To make the two genuine peers, the internal `ActiveEffect` record stops wrapping a
`StaticContinuousEffect` and carries the layer payload directly:

```kotlin
internal data class ActiveEffect(
    val source: ObjectId?,                       // null: an ability's source may be gone (CR 113.7c)
    val affected: ObjectId,
    val grantedKeywords: PersistentSet<Keyword>,
    val grantedManaAbilities: PersistentList<ManaAbility>,
    val powerMod: Magnitude,
    val toughnessMod: Magnitude,
    val timestamp: Long,
)
```

A static effect contributes its declared `Magnitude`s; a timed effect contributes
`Magnitude.Fixed(powerMod)` / `Magnitude.Fixed(toughnessMod)`. `layersOf` and `applyLayer` are
otherwise untouched, including the loud gate — which now also catches a timed effect that grants
nothing and modifies nothing.

**This is the whole of the layer-engine change**, and it is what `layer-system.md` §2 meant by
"concatenates a second, timestamped, expiring source without reshaping anything downstream".

**A timed effect whose `affected` object has left the battlefield contributes nothing, and is not an
error.** CR 611.2 effects do not cease when their object dies; the object that comes back is a new
one (CR 400.7), so the effect simply has nothing to apply to for the rest of the turn. The collector
filters on `affected == affectedId`, so a dangling entry is skipped by construction — and, crucially,
the §8 invariant must **not** require the affected object to exist, which is the mistake an
`ATTACHMENT_INTEGRITY`-shaped check would make here.

### 5.3 Creation — one published effect primitive

`mtg-rules/effect/UntilEndOfTurn.kt`, in the house style of `destroy`/`dealDamage`:

```kotlin
fun applyUntilEndOfTurn(
    state: GameState,
    affected: ObjectId,
    modification: ContinuousModification,
    sourceCard: CardRef,
    source: ObjectId? = null,
): GameState
```

It requires `affected` to be a current battlefield object (CR 611.2c — every caller arrives after the
CR 608.2b re-check, so absence is an engine defect), allocates the timestamp, appends to the store,
and emits `GameEvent.ContinuousEffectCreated`. The "effect must do something" gate lives one level
down, in `ContinuousModification`'s constructor.

The **count** a snapshot needs is not this function's business. `mtg-rules` already has the
`PermanentFilter` count `cost-modification.md` §6 asked for, hidden as a private
`countMatching` inside `ManaSourceClass.kt`. This packet lifts it — unchanged in behaviour — into
`engine/PermanentCount.kt` as `countMatchingPermanents(state, filter, you)`, with `ManaSourceClass`
delegating. That is §6's "extract the predicate and the count; do not extract the consumer", done at
the first moment there are two consumers.

### 5.4 Cleanup — CR 514.2, and the ordering that is a real bug if got wrong

`cleanupRemoveDamageAndEndEffects` finally does both halves of its name, **in one transition**:
marked damage is cleared and every `UntilEndOfTurn` effect is dropped, simultaneously.

CR 514.2 makes these two turn-based actions simultaneous, and it is not a formality. Concretely, with
Timberwatch Elf on the board:

> A 1/2 is pumped to a 4/5 and takes 4 combat damage. It survives (4 < 5). At cleanup, if the pump
> ended *before* the damage cleared, the creature would momentarily be a 1/2 with 4 marked damage and
> die to CR 704.5g. Because the two are simultaneous, it survives with 0 damage.

That is a reachable, silently-wrong outcome that no existing test would catch, and it is the headline
acceptance case (§10). It also explains why the store is cleared inside
`cleanupRemoveDamageAndEndEffects` rather than anywhere adjacent to it.

**Interaction with CR 704 state-based actions.** `finishCleanup` already runs
`performStateBasedActions` after the turn-based actions and honours CR 514.3a (if any SBA performed
work, or a trigger is waiting, players receive priority and another cleanup step follows). That
sequencing is correct as it stands and is not changed. What is worth recording is *whether the second
cleanup is reachable from a wear-off*:

- A **positive** P/T modifier wearing off lowers toughness — but only in the same instant that all
  marked damage is removed, so CR 704.5g cannot fire from it. CR 704.5f (toughness 0 or less) cannot
  fire either: a positive modifier wearing off returns the creature to its printed toughness, which
  `PrintedPowerToughness` requires to be a real number and which was survivable before the pump.
- A **negative** modifier wearing off raises toughness and can only *prevent* a death.

So no CR 514.2 wear-off in this packet's effect set can make a state-based action applicable, and the
CR 514.3a repeat stays unreachable from durations. This is a correct-by-construction claim over the
closed list — the same shape of argument as §2.2's — and the first effect kind that breaks it (a
delayed "destroy it at end of turn", a set-P/T wearing off) reaches the existing repeat path, which
already works.

## 6. Compute-on-read, revisited

`layer-system.md` §5 chose compute-on-read over a materialised cache, on the grounds that a dynamic
magnitude has no invalidation hook under structural sharing. Durations make that decision *more*
right, in a way worth recording because the opposite intuition is available.

A tempting alternative is to write the pump into the object — bump a `GameObject.powerBonus` field
and decrement it at cleanup. It is simpler to read and it is wrong twice over: the value would
survive the object (CR 400.7 says the dying creature and the graveyard card are different objects,
and a bonus field would have to be manually stripped like `tapped` is), and it would make the layer
order unrepresentable — a stored bonus has no timestamp and no layer, so it could never be ordered
against an Aura's. Keeping the effect in a store and computing on read keeps CR 613 the only place
characteristics are decided.

The performance note stands unchanged: the store is bounded by the effects created this turn (a
handful), each read is O(board + store), and the fix if profiling ever demands one is a transient
per-pass memo, never a stored cache.

## 7. The replay-fingerprint token

`layer-system.md` §5 ruled that the fingerprint digests the **cause** of a continuous effect, never
its computed values: two states differing in continuous effects necessarily differ in which Auras are
attached where, which the residence lines already carry.

A timed effect is a cause with no residence line — the first rules-relevant fact in `GameState` that
is not an object and not a pending decision. Left undigested, two states differing *only* in whether
a pump resolved would hash identically, and a replay divergence at exactly that point would be
invisible. So the ruling does not change; it forces a token.

**New token, one line per effect, appended after the pending positions:**

```
|timed=<affected>:<pow>/<tou>:<kw+kw>:<duration>@<timestamp>:<sourceCard>@<source>
```

Digested in store order, which is creation order, which is timestamp order — so the token is
order-stable by the same append-only property the invariant checks (§8). The snapshotted integers
*are* the cause here, not a computed value: they were fixed at creation and no state the digest
covers determines them any more (the Gate count that produced a `+3/+3` may since have changed).
Digesting them is therefore consistent with §5's rule, not an exception to it — and omitting them
would let two states with differently-sized pumps hash alike.

`createdOnTurn` is deliberately *not* in the token: it is implied by `turn.number` for every effect
the store may legally hold (§8), so digesting it would add a byte that can never vary independently.

## 8. The new invariant

**`Invariant.TIMED_EFFECT_SANITY`**, checked by `checkTimedEffectSanity(state)` in the acceptance
invariant checker (DoD item 4). Three properties, chosen because each is a *guarantee* rather than a
plausible-sounding restatement:

1. **The duration is honoured.** Every `UntilEndOfTurn` effect has `createdOnTurn == turn.number`.
   This is the whole contract: a CR 514.2 wear-off that failed to fire is caught at the very next
   observed pause, on the following turn, rather than surviving as a permanent-looking pump. It is
   the reason `createdOnTurn` is stored.
2. **The timestamp sequence is sane.** Every timestamp is strictly below `nextObjectId` (CR 400.7's
   bound, now covering the shared creation sequence, §4), and timestamps are strictly increasing in
   store order — the append-only property the fingerprint's order-stability and the CR 613.7 sort
   both rest on.
3. **Every stored effect does something.** A timed effect with no granted keyword and both modifiers
   zero is an unimplemented effect kind that was silently dropped into the store. This is
   `layer-system.md` §1's loud gate, restated as a state property so that a bad effect is caught even
   on a turn when nothing reads the affected object's characteristics.

**What the invariant deliberately does *not* check** is the mistake an `ATTACHMENT_INTEGRITY`-shaped
check would make: it does **not** require `affected` to name a current battlefield object. A timed
effect outliving its target is correct (§5.2), and asserting otherwise would fail the moment a pumped
creature dies — which is a common line of play, not a bug.

No game-over exemption is needed. Unlike `CREATURE_LETHALITY_RESOLVED` and `ATTACHMENT_INTEGRITY`,
none of these three properties depends on state-based actions having run to quiescence, so they hold
in the final game-over state exactly as they do at any other pause.

## 9. The cards — one carried, six dropped, each with its precise blocker

The scope rule is the brief's: anything needing a framework this packet does not own is dropped, with
the missing piece named. Six of seven are dropped, which is itself the finding — `FW-DURATION` is
counted at 13 cards in the triage but **unlocks 3 alone**, and this packet is the empirical
confirmation of that ratio.

### 9.1 Basilisk Gate — dropped; needs `FW-ABILTGT`-adjacent timing, and trap T17

`Land — Gate`. `{T}: Add {C}.` / `{2}, {T}: Target creature gets +X/+X until end of turn, where X is
the number of Gates you control. Activate only as a sorcery.`

The duration half is exactly what this packet builds, and the snapshot ruling (§3) is written for it.
Two blockers, neither owned here:

- **"Activate only as a sorcery" does not exist.** `ActivatedAbility` has no timing restriction;
  `TimingClass` is declared on `SpellDefinition` only, and `ActivationGathering`/`Activation`
  enumerate an ability whenever its cost is payable. Encoding the Gate without it would make an
  instant-speed combat trick out of a card that is deliberately not one — an
  enumerated-but-illegal action (ADR-005). This needs an `ActivatedAbility.timing` field and an
  enumeration gate, which is activation machinery, not duration machinery.
- **Trap T17 fires on it exactly.** The Gate is *both* a mana source and the source of a `{T}`-costed
  ability with a mana component. `abilityCostPayable` and the activation's payment request both call
  `enumeratePaymentPlans`, which does not know which source is paying, so the enumerator offers a
  plan that taps the Gate for `{C}` toward its own `{2}` — and `tapObjectForCost` then throws
  `CR 602.2a: a {T} cost requires an untapped source`. The triage names Basilisk Gate as one of seven
  cards that would be the first to reach this, and the fix belongs to
  `manaSourceClasses`/`enumeratePaymentPlans` (ownership: `FW-MANA`/payment), not here.

Timberwatch Elf carries the identical duration+snapshot semantics with neither blocker, so nothing
about the framework goes untested by dropping the Gate.

### 9.2 Tamiyo's Safekeeping and Brinebarrow Intruder — dropped; both need a decider-relative `PermanentRestriction`

- *Tamiyo's Safekeeping* — `{G}` Instant. "Target permanent **you control** gains hexproof and
  indestructible until end of turn. You gain 2 life."
- *Brinebarrow Intruder* — `{U}` Creature — Human Rogue, 1/2, Flash. "When this creature enters,
  target creature **an opponent controls** gets -2/-0 until end of turn."

Everything else about these two is in hand. `Keyword.HEXPROOF` and `Keyword.INDESTRUCTIBLE` both
exist and are both read through live seams (`targetableBy`, `isIndestructible`), so a *granted*
hexproof already restricts an opponent's target enumeration and a granted indestructible already
survives `destroy` and CR 704.5g. `gainLife` exists. `FW-ABILTGT` has landed, so the Intruder's
targeting ETB has a home. The negative modifier is a plain integer in this design.

The single shared blocker is the target line. `PermanentRestriction` has five members and **none is
controller-relative**; `satisfiesPermanentRestriction(state, restriction, candidate)` does not even
take the deciding player. Adding "permanent you control" / "creature an opponent controls" means
threading `you` into that predicate and into its call in `Targets.kt` — the file this packet is
explicitly barred from, and for good reason: `Targets.kt` is the single definition of target legality
that the cast-time enumeration, the CR 608.2b re-check, and the agent's option list all share, and
five packets are in flight against it. Using `TargetSpec.TargetPermanent(CREATURE)` and ignoring the
control clause would be a silently-wrong encoding of a card whose whole point is which side it hits;
borrowing `TargetSpec.Enchantable(CREATURE_YOU_CONTROL)`, which *is* controller-relative, would put
attachment semantics on an instant.

**Precisely what they need:** two `PermanentRestriction` members (`PERMANENT_YOU_CONTROL`,
`CREATURE_AN_OPPONENT_CONTROLS`), a `you: PlayerId` parameter on
`satisfiesPermanentRestriction`, and the corresponding one-line change in `legalTargets`. Brinebarrow
additionally needs **Flash** — expressible today as `TimingClass.INSTANT_SPEED` on a creature
`SpellDefinition`, which the type already permits and whose KDoc explicitly anticipates
("later phases can grant instant-speed to sorcery-typed cards"), so Flash is *not* a blocker; only
the restriction is.

Both are one small targeting packet away, and both should land in the packet that owns
`PermanentRestriction`, not this one.

### 9.3 Toxin Analysis — dropped; needs `Keyword.DEATHTOUCH` and the CR 702.2b rule behind it

`{B}` Instant. "Target creature gains deathtouch and lifelink until end of turn. Investigate."

The target spec exists (`TargetPermanent(CREATURE)`), `Keyword.LIFELINK` exists and is honoured in
damage results, and Investigate is close to Tier 0 — a token with
`{2}, Sacrifice this token: Draw a card` composes `createToken`, `AbilityCost.Mana`,
`AbilityCost.SacrificeSelf`, and `drawCards`, all published.

**Deathtouch is the blocker, and it is not a one-line enum addition.** `Keyword.kt` is outside this
packet's ownership, and adding the member is the smaller half anyway: CR 702.2b makes *any* nonzero
damage from a deathtouch source lethal, which changes the CR 704.5g state-based action, the
CR 510.1a/c lethal-damage assignment in combat, and trample's "damage above lethal" computation
(`TrampleAssignment.kt`) — three rules sites that today all read `effectiveToughness` directly.
Deathtouch is a small framework, not a keyword flag.

Encoding the card with only lifelink would be a half-card that looks whole in a game log. Dropped.

### 9.4 Goblin Bushwhacker — dropped; four frameworks, none of them this one

`{R}` Creature — Goblin Warrior, 1/1. "Kicker {R}. When this creature enters, if it was kicked,
creatures you control get +1/+0 and gain haste until end of turn."

The brief's instruction to drop it if it has kicker is confirmed by the oracle text, and kicker is
only the first of four:

1. **Kicker (CR 702.33)** — an optional additional cost chosen at CR 601.2b. `AdditionalCost` has one
   member (`DiscardCards`) and no optional-mana shape; ownership `FW-OPTCOST`, and `AdditionalCost`
   is explicitly outside this packet.
2. **Linked information "if it was kicked"** — the trigger must read a fact about how the spell was
   *cast*, which is a `ResolutionContext`/`StackEntry` extension in the shape of `discardedForCost`.
3. **Intervening-if (CR 603.4)** — `TriggeredAbility`'s KDoc records that this is unmodelled and
   deliberately separate.
4. **An `AffectedSet` wider than `Enchanted`** — "creatures you control" is a computed set evaluated
   at effect creation (CR 611.2c). This packet deliberately builds one affected object, not a set
   (§5.1); widening it is `FW-CONDSTATIC`.
5. **Haste** — see §9.5.

### 9.5 Rally at the Hornburg — dropped; needs haste and a computed affected set

`{1}{R}` Sorcery. "Create two 1/1 white Human Soldier creature tokens. Humans you control gain haste
until end of turn."

`createToken` exists and the tokens are Tier 0. Both remaining halves are outside this packet:

- **Haste is not in `Keyword`** (`Keyword.kt` is not this packet's file), and — like deathtouch — the
  enum member is the smaller half. Haste (CR 702.10b) is a *negation of a restriction*: it must be
  read by the CR 302.6 summoning-sickness gate in **two** places that currently test
  `obj.summoningSick` directly — `Activation.kt`'s `{T}`-cost check and `ManaSourceUsability`'s
  `manaSourceUsable` — plus `CombatActions`' attack declaration. Adding the keyword without rerouting
  all three would produce a hasty creature that still cannot attack: silently wrong, and plausible.
- **"Humans you control" is a computed affected set**, the same `FW-CONDSTATIC` gap as §9.4, with the
  extra wrinkle that CR 611.2c locks the set at resolution — a Human created *after* the spell
  resolves does **not** gain haste. That is a second snapshot semantics, adjacent to §3's but not the
  same one, and it deserves its own note rather than a rushed member here.

### 9.6 Timberwatch Elf — carried

`{2}{G}` Creature — Elf, 1/2. `{T}: Target creature gets +X/+X until end of turn, where X is the
number of Elves on the battlefield.`

Everything it needs exists or is built here:

| Requirement | Status |
|---|---|
| Targeted **activated** ability | `ActivatedAbility.targetSpec` (`FW-ABILTGT`, landed) |
| "target creature" | `TargetSpec.TargetPermanent(PermanentRestriction.CREATURE)` — not controller-relative |
| `{T}` cost, CR 302.6 summoning sickness | `AbilityCost.TapSelf`, gated in `Activation.kt` |
| Not a mana source | true — so trap **T17** is unreachable from it |
| Count of Elves **on the battlefield** (both sides) | `PermanentFilter(Subtype("Elf"), controlledByYou = false)` + `countMatchingPermanents` (§5.3) |
| Snapshotted X | §3 — the count runs in the resolution effect, the store holds an `Int` |
| Until end of turn | this packet |

Three oracle details that are easy to get subtly wrong and are asserted individually (§10): the count
is **all** Elves, not Elves you control (the `controlledByYou = false` boolean, exactly as on Priest
of Titania); **it counts itself**, so a lone Timberwatch Elf gives +1/+1; and the count is taken
**once, on resolution** (CR 608.2h), not live.

It is in the Elves mainboard at 4 copies, so it moves the `GauntletCoverageSpec` burn-down.

## 10. Test strategy

**`mtg-rules` unit tests** (fixture cards only — the module names no card):

- *CR 611.2d: a snapshotted magnitude does not change when the board does* — the §3.3 property.
- *CR 613.3c: a static aura's dynamic magnitude still tracks the board* — the mirror, on a board that
  also carries a timed effect.
- *CR 613.7d: a timed effect's timestamp orders against an Aura's in one sequence* — an Aura entering
  after an ability resolves sorts after it, and vice versa.
- *CR 613.1f / 613.4d: a timed grant lands in layer 6 and a timed modifier in sublayer 7c* — layer
  isolation, restated for the new source.
- *CR 611.2c: a timed effect whose affected object has left the battlefield applies to nothing* — and
  specifically does not follow the card into its next zone (CR 400.7).
- *CR 613: a timed effect that grants nothing and modifies nothing fails loudly* — the loud gate, at
  creation and at application.
- *CR 514.2: the cleanup step ends every until-end-of-turn effect* — the store is empty afterwards.
- *CR 611.2: a timed effect stacks additively with an Aura on the same creature.*

**`mtg-cards` tests** — Timberwatch Elf's three oracle details from §9.6.

**`mtg-acceptance`:**

- The headline ordering case, as a scripted game: *CR 514.2: a creature kept alive by an
  until-end-of-turn pump survives cleanup, because damage removal and the wear-off are simultaneous.*
  This is the test that would fail if the two halves were sequenced.
- *CR 704.5g: a creature pumped past lethal damage does not die mid-turn* — the pump's effect on the
  existing lethality state-based action, via the layered accessor.
- *CR 608.2b: an activated ability whose target has died fizzles and creates no timed effect* — the
  store stays empty, which is the observable consequence.
- The **layer oracle** (`OracleCharacteristics`) is extended to sum timed effects from the store,
  keeping its independence rule: it reads the store's integers directly and references no layer
  classification code.
- The **invariant checker** gains `TIMED_EFFECT_SANITY` with a unit test per property, including
  against corruption a real `GameState` cannot reach (an effect stamped with a past turn).
- The **fingerprint** gains a test that two states differing only in a stored pump hash apart.

## 12. Non-goals (explicit)

Each is a slot the design reserves and a loud gate refuses to fake.

- **Durations other than end of turn.** `EffectDuration` is sealed with one member, so
  "until your next turn" (Reckless Impulse), "until end of your next turn" (Clockwork Percussionist),
  and "until this leaves the battlefield" each break the cleanup `when` rather than silently
  expiring at the wrong time.
- **Delayed triggered abilities (CR 603.7)** — "at the beginning of the next end step, sacrifice it".
  A stored *trigger*, not a stored continuous effect; different machinery, adjacent slot.
- **Scheduled rule modifications** — "skips their next combat phase" (Stonehorn Dignitary), "doesn't
  untap during its controller's next untap step" (Sleep of the Dead). These modify the turn structure,
  not characteristics, and belong nowhere near the layer collector.
- **Duration-bounded *permission*** — "until end of your next turn you may play those cards"
  (Reckless Impulse). A casting permission with a deadline, not a continuous effect.
- **Computed affected sets** (`FW-CONDSTATIC`) — §9.4/§9.5.
- **CR 615 prevention shields** (`FW-PREVENT`) — may share the store's *duration* machinery, must not
  share `activeEffectsOn` (§2.3).
- **CR 613.8 dependency ordering** — unchanged from `layer-system.md` §3, still
  correct-by-construction over the closed additive list.
- **Timed effects in unpopulated layers** — a timed type-change or set-P/T hits the existing
  `applyLayer` gate exactly as a static one does.

## 13. Protocol versioning

`PROTOCOL_VERSION` stands at **`5.0.0`** (`FW-COUNTER` + `FW-MANA`). **Call: bump to `6.0.0`.**

The break is server→client only and narrower than `5.0.0`'s, but it is a break on the standard the
last four versions set: `SeatViewDto` gains a **required** `timedEffects` list, and the codec is
strict about unknown fields, so a `5.0.0` peer rejects a `6.0.0` seat view outright. That is the same
break shape `4.0.0` recorded for `pendingLibraryLook` and `3.0.0` for `pendingTriggerTargets`, and
the recorded standard is to say so with a major bump rather than to argue that nobody is listening.

The client→server direction is **unchanged**: this framework adds no `DecisionRequest` kind, no
`Target` member, and no field to any request or answer. An until-end-of-turn effect is something an
agent *observes*, never something it decides — which is why the break is the mild kind (a strict-codec
rejection at decode) rather than `4.0.0`/`5.0.0`'s runtime `valueOf` failure mid-match.

Five framework packets are in flight against `5.0.0`. If another lands first, the honest merge is a
single `6.0.0` carrying both breaks, on `5.0.0`'s own precedent ("neither shipped separately, so
`4.0.0` is the last version any consumer can have seen"). Flagged in the packet report.

## 14. Open questions for the architect

1. **Timestamp sourcing** (§4): draw timed-effect timestamps from `nextObjectId` — one total order,
   no new counter (recommended, and argued as a correctness requirement rather than an economy) —
   versus a dedicated timestamp counter and a comparison rule between the two sequences.
2. **`ActiveEffect` reshaping** (§5.2): carrying the layer payload directly, so a static and a timed
   effect are peers, versus keeping `StaticContinuousEffect` as the payload and accepting a
   meaningless `affects` value on the timed side.
3. **Snapshot representation** (§3.2): plain `Int` on the stored effect, with the count performed by
   the resolution effect — versus a `Magnitude.Snapshot(value)` member for symmetry. This note argues
   the plain `Int` makes T16's failure a type error.
4. **`createdOnTurn` on the stored effect** (§5.1, §8): stored solely so the duration contract is
   machine-checkable, versus dropping it and losing the invariant's first property.
5. **Fingerprint content** (§7): digesting the snapshotted integers is argued to be consistent with
   `layer-system.md` §5's cause-not-effect rule (they *are* the cause once frozen). Confirm.
6. **Card scope** (§9): one card of seven carried. Confirm that dropping five to targeting/keyword
   frameworks and one to kicker is preferred to encoding any of them approximately.
7. **`countMatchingPermanents` extraction** (§5.3): lifting `ManaSourceClass.kt`'s private count into
   a shared internal — `cost-modification.md` §6's recommendation, executed at the first second
   consumer — touches a file owned by `FW-MANA`. Confirm, or duplicate.
