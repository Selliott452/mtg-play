# ADR-002: Immutable game state with structural sharing

## Status

Accepted

## Context

An AI-training engine constantly replays, forks, and snapshots game states: RL rollouts
branch, tests assert on before/after pairs, and replay reconstructs a game from its inputs
(ADR-006). Mutable, shared state makes all of these fragile — aliasing bugs, accidental
mutation of a state another consumer still holds, and non-reproducibility. MTG state is also
large (zones, stack, continuous effects), so a naive full copy on every transition would be
wasteful.

## Decision

`GameState` is immutable. Every engine transition returns a **new** `GameState`; nothing
mutates in place. Collections held in state use `kotlinx.collections.immutable` persistent
data structures, so unchanged substructure is shared between successive states (structural
sharing) and per-transition allocation is proportional to what changed, not to total state
size. Core types validate their invariants on construction ("nouns in core", PLAN.md §3) but
never advance the game.

## Consequences

- Any previous state is a valid, independent value: forking a search, retaining history for
  replay, and snapshotting in tests need no defensive copying.
- Structural sharing keeps immutability affordable, which is what makes retaining states for
  the event log and replay (ADR-006) practical.
- Transition code is written as pure functions that thread state through and return it; this
  is a discipline the whole engine must keep.
- `kotlinx.collections.immutable` is a sanctioned dependency of `mtg-core` (PLAN.md §3) and
  the default for any collection held in state.
- **Rules out:** in-place mutation of game state; `MutableList`/`ArrayList`/`var` collections
  as fields of state types; `advance`-style methods that return `Unit` and mutate a receiver.
