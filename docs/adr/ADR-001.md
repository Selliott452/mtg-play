# ADR-001: Build the engine from scratch in Kotlin

## Status

Accepted

## Context

Mature open-source MTG engines exist (Forge, XMage). Reusing one would save
implementation effort, but both are large Java codebases shaped by goals we do not share:
a GUI client, a broad unversioned card pool, and human-facing play rather than programmatic,
reproducible, per-decision control. Our objective is a headless, deterministic, fully
enumerable rules engine that serves AI agents through an in-process Kotlin API (ADR-004,
ADR-005). We also need a codebase whose architecture we fully control, so the load-bearing
guarantees — immutability (ADR-002), determinism (ADR-006), per-seat filtering (ADR-007) —
hold end to end rather than being retrofitted onto someone else's design.

## Decision

Build the engine from scratch in Kotlin (latest stable, on JVM 21). Forge and XMage are
permitted as **reference reading only** — for understanding Comprehensive Rules corner cases
and for cross-checking our own behaviour — and are never build dependencies. We do not port,
vendor, or copy their code. Card *metadata* comes from Scryfall (ADR-003); rules *behaviour*
is ours.

## Consequences

- Full control over state representation and API shape; immutability, determinism, and
  filtering are designed in, not bolted on.
- Comprehensive Rules coverage grows incrementally, scoped to the Pauper MVP pool
  (`docs/decklists.md`). We ship correctness for what the decks need and fail loudly
  elsewhere (ADR / PLAN.md §4).
- Higher up-front implementation cost than adopting an existing engine; accepted deliberately
  (correctness and control over speed of implementation, PLAN.md §4).
- The licence for our own code (deferred to Phase 8) is unencumbered by any engine we merely
  read.
- **Rules out:** depending on, vendoring, or porting Forge/XMage or any third-party engine;
  copying their code or inheriting their licence obligations. Consulting them to understand a
  rule is fine; lifting their implementation is not.
