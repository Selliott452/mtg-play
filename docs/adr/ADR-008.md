# ADR-008: Match protocol is JSON over WebSocket, layered on the library

## Status

Accepted

## Context

Agents and clients in separate processes — a reference client, a random agent, a remote
trainer — need to drive matches over a network. But the primary, first-class interface for AI
is the **in-process Kotlin API** (ADR-004). The protocol must not become a second, divergent
engine interface that can drift from the library's semantics.

## Decision

The match protocol is **JSON over WebSocket**, implemented in `mtg-protocol` as a thin layer
**on top of the library**. Protocol messages **mirror the ADR-004 decision model**: the server
sends the deciding seat its filtered state (ADR-007) and a `DecisionRequest` with enumerated
options; the client replies with a `Decision` (request id + selected index, ADR-005).
Serialization uses `kotlinx.serialization`, and the message schema is versioned. The
**in-process Kotlin API remains the primary AI interface**; the protocol is a transport over
it, not a replacement.

## Consequences

- Networked and in-process play share one decision model, so agents port between them with
  minimal change and the wire format cannot drift from the engine's semantics.
- The protocol inherits enumerated actions (ADR-005), determinism (ADR-006), and per-seat
  filtering (ADR-007) for free — it transports them rather than reimplementing them.
- A versioned schema lets the wire format evolve without breaking the in-process API.
- **Rules out:** a protocol that exposes engine capabilities the in-process API lacks (or vice
  versa); freeform action messages; sending unfiltered state over the wire; making the network
  layer the primary or authoritative interface to the engine.

## Amendment (Phase 7 planning, 2026-07-23)

The protocol decomposes into three parts with distinct homes:

1. **Per-seat filtering (ADR-007)** is rules knowledge and lives in `mtg-rules` as a pure
   public derivation (`viewFor(state, seat)` beside `pendingRequestOf`) — never in a consumer,
   because a wrong filter is a silent information leak to a training agent.
2. **The message schema + codec** live in `mtg-protocol` as a **transport-free** artifact:
   pure DTOs + `kotlinx.serialization`, no server dependencies. Same-repo placement makes a
   new `DecisionRequest` kind a compile-time schema break (the exhaustive-`when` discipline)
   rather than silent consumer drift, and locks schema versions to engine versions.
3. **The server** is a thin reference implementation only (WebSocket host, match lifecycle,
   seat tokens) — executable documentation of the schema, dependency-isolated from it so
   library consumers never inherit the web stack. Operational concerns (matchmaking,
   persistence, real auth) belong to consumers permanently.
