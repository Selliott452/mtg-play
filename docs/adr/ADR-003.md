# ADR-003: Card rules in a Kotlin DSL over published primitives; metadata from Scryfall

## Status

Accepted

## Context

Encoding hundreds of cards must not devolve into hundreds of bespoke special cases — the
failure mode that makes rules engines unmaintainable (PLAN.md §7). Cards differ in *data*,
not in *kind*: "deal N damage to any target", "when this enters, create a token", "add one
mana of any color". We also need authoritative, legally usable card metadata (names, mana
costs, type lines, oracle text).

## Decision

Card behaviour is authored in a **type-safe Kotlin DSL** (in `mtg-cards`) that composes
**published primitives** exposed by `mtg-rules` — damage, targeting, token creation,
cost/timing modifiers, and so on. Card metadata is ingested from **Scryfall bulk data**.

**Vocabulary discipline (the load-bearing rule):** a card definition may use only
already-published DSL primitives. If a card needs a behaviour no primitive expresses, that
primitive is added to `mtg-rules`/the DSL **with its own unit tests first, in the same
packet**, and called out in the packet report. Card-local special-casing is prohibited, and
`mtg-rules` never references a specific card (PLAN.md §3).

## Consequences

- Card files stay declarative and reviewable; correctness concentrates in a small, tested
  primitive vocabulary instead of being smeared across every card.
- New mechanics have a single home and a test gate; the vocabulary grows deliberately — the
  mitigation for "DSL devolves into per-card special cases" (PLAN.md §7).
- Scryfall bulk data is licensed **CC BY 4.0**: attribution is an obligation, carried in the
  README when ingestion lands (P6.1). Scryfall data is metadata only and does not encode
  executable rules.
- **Rules out:** hard-coding a card's behaviour with logic that bypasses the DSL; card-specific
  branches inside `mtg-rules`; shipping a card that needs a new primitive without also shipping
  and testing that primitive; treating Scryfall oracle text as executable rules.
